# Repository Guidelines

## Правила проекта

- HelpDesk — учебный REST API. Пиши готовый код только по прямой просьбе пользователя. В остальных случаях объясняй решения, давай небольшие задания и проверяй реализацию. Для каждой найденной ошибки указывай сценарий и причину.
- Перед изменением изучи актуальные файлы. Не добавляй зависимости без согласования. Не меняй код, не связанный с заданием. Сохраняй существующую архитектуру.

## Состояние на 17 ноября 2026 года

Основной код находится в `src/main/java/com/helpdesk/HelpDesk/`. Есть пять JPA-сущностей с репозиториями, DTO, ручные мапперы, `UserService`, `CategoryService` и частичный `TicketService`. В Security настроен BCrypt. JWT и контроллеры `/api/v1` запланированы.

`createTicket` уже проверяет категорию, задаёт `OPEN`, приоритет из запроса, даты, `assignedTo = null` и `isArchived = false`. Остаётся заполнить `createdBy`. Смена статуса обновляет дату и записывает историю без обязательного `actor`. Смена приоритета пока лишь сохраняет значение. Общий список исключает архив, выборка по статусу — нет.

## Бизнес-правила

- **CUSTOMER** создаёт тикеты, читает и комментирует свои. После создания редактирование ему недоступно. **SUPPORT** видит рабочую очередь, комментирует, меняет статус, приоритет и исполнителя. **ADMIN** дополнительно управляет пользователями, категориями и архивом.
- Роль существующего ADMIN меняется только вручную в БД. Блокировать активного ADMIN вправе только другой ADMIN. После операции должны оставаться минимум два активных администратора, в том числе при конкурентных запросах. Проверяй минимум только при фактической блокировке.
- Из `OPEN` тикет переходит только в `IN_PROGRESS`. Из `IN_PROGRESS` разрешены переходы в `WAITING_FOR_CUSTOMER` и `RESOLVED`. Из `WAITING_FOR_CUSTOMER` можно вернуться в `IN_PROGRESS` или сразу перейти в `RESOLVED`. Прямой переход `WAITING_FOR_CUSTOMER → RESOLVED` — осознанное решение проекта. Из `RESOLVED` возможен только переход в `CLOSED`. Статус `CLOSED` терминальный.
- Комментарии публичны. В CLOSED и архиве новые комментарии запрещены. Архивирование сохраняет статус, комментарии и историю. ADMIN и SUPPORT могут просматривать все архивные тикеты. CUSTOMER может просматривать все свои тикеты независимо от статуса и признака архивирования, включая CLOSED и архивные. Эти права действуют для списков и получения отдельного тикета по ID. Архив доступен только для чтения.
- Архивировать тикет может ADMIN, если тикет ещё не архивирован, имеет статус `RESOLVED` или `CLOSED` и с момента его создания прошёл как минимум один календарный месяц. Граница включительна — архивирование разрешено начиная с `createdAt.plusMonths(1)`. Возраст отсчитывается от создания тикета.
- Получай создателя, автора комментария и инициатора изменения из Security Context. Изменение тикета, обновление `updatedAt` и запись истории выполняй в одной транзакции. История доступна через API только для чтения.

## Следующий этап

Спроектируй отдельную операцию назначения. Предложенные условия: активный SUPPORT или ADMIN, включая самоназначение сотрудника, переназначение и снятие через `assigneeId = null`. Затем запланированы архивирование, JWT, завершение проверок доступа и аудита, сервисы комментариев и истории, контроллеры, фильтрация и пагинация.

## Разработка и проверка

- Java 21, Spring Boot 4.1.2, PostgreSQL 18.1. Используй четыре пробела, constructor injection и `final` для зависимостей. Бизнес-правила размещай в сервисах, границу HTTP оформляй через валидируемые DTO. Исключай пароль из ответов.
- Скопируй `.env.example` в `.env`, заполни параметры PostgreSQL. Не коммить секреты. `make env-up` запускает БД, `make app-run` — приложение, `make env-down` останавливает БД.
- Добавляй новые миграции в `src/main/resources/db/migration/`. Уже применённые не редактируй. В репозитории есть `V3__add_user_enabled.sql`. Hibernate проверяет схему `helpdesk` через `ddl-auto=validate`.
- Экспортируй переменные БД перед `./mvnw test` или полной сборкой `./mvnw clean verify`. В `src/test/java` пока один тест загрузки контекста на JUnit Jupiter. Именуй тесты `*Test` или `*Tests`; в первую очередь проверяй переходы статусов, права, архив и ограничения ADMIN.

## Git и Pull Requests

Начинай логический этап в отдельной ветке от обновлённой `main`. Пиши короткие предметные сообщения коммитов. В PR опиши изменение поведения, связанные задачи, миграции и результаты проверок. Используй Squash and merge через GitHub. Локально сливай ветку в `main` только по прямой просьбе.
